# Phase 4: fine-tuning workflow

Phase 3 (training-data generation) is done: 301 examples in `data/train/train_pilot.jsonl`,
generated by `training_pairs.py` + `build_training_set.py` against the real RAG retrieval, with
zero warnings. This doc is the plan for turning that into a fine-tuned model and proving it's
actually better than the 94% RAG baseline, before it goes anywhere near production.

Nothing in this phase touches `data/eval/eval_set.jsonl` - that 216-question set stays
completely unseen until the very last step, so it's still a fair acceptance test.

## 0. Split train/dev (on the Mac, in the venv - this part is cheap)

```
python split_train_dev.py
```

Stratified 15% dev split by category, seeded for reproducibility. Writes
`data/train/train.jsonl` (~256 examples) and `data/train/dev.jsonl` (~45 examples). The dev
split isn't the acceptance test - it's just so the trainer can report `eval_loss` during the
run and catch a broken/overfit run early. Covered by `pytest -q` (`tests/test_split_train_dev.py`).

## 1. Get a rented GPU

The Mac's 8-16GB unified memory can't fit a QLoRA fine-tune of an 8B model comfortably. Use
one of:
- **RunPod**: rent a single GPU pod (a T4, L4, or A10 - 16GB+ VRAM is enough for 4-bit QLoRA
  on an 8B model with a ~300-example dataset). Pick a template with PyTorch + CUDA already on
  it if available.
- **Google Colab**: a free or Pro T4/A100 session works too, and skips the rental step
  entirely - simplest option if you don't need a specific pod type.

Either way, this should be well under an hour of GPU time for a dataset this size.

## 2. Set up the GPU box

Upload (or `git clone`) this project to the GPU box, then:

```
pip install -r requirements-train.txt
```

This installs Unsloth + TRL + PEFT + bitsandbytes - none of this touches the Mac's `.venv`,
which stays as-is for the RAG app.

You only need `data/train/train.jsonl`, `data/train/dev.jsonl`, and `train_qlora.py` on the
GPU box - the rest of the repo (rag.py, chroma_db, etc.) isn't needed there.

## 3. Run the fine-tune

```
python train_qlora.py --train data/train/train.jsonl --dev data/train/dev.jsonl --out lora_out --epochs 3
```

Defaults: `unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit` as the base (Unsloth's ungated 4-bit
mirror of the same weights the `llama3.1:8b` Ollama model uses), LoRA rank 16, 3 epochs,
cosine LR schedule. Adjust `--epochs`, `--lora-r`, `--learning-rate` etc. if the loss curve
looks off (e.g. `eval_loss` climbing while `train_loss` keeps falling means overfitting - try
fewer epochs or a lower rank).

This writes the LoRA adapter (a few hundred MB, not a full model) to `lora_out/`. Download
that folder back - that's the only artifact you need from the GPU box.

## 4. Turn the adapter into something Ollama can run

Two options, in order of how much extra tooling they need:

**Option A - export straight to GGUF on the GPU box** (simplest, do this before leaving the
GPU box): uncomment the `save_pretrained_gguf` line at the bottom of `train_qlora.py` and
re-run just that line (or add it to your training script call) - it needs `llama.cpp`
available, which Unsloth can fetch for you. Produces a `.gguf` file directly.

**Option B - merge + convert separately**: merge the LoRA adapter into the base weights with
`model.save_pretrained_merged(...)` (Unsloth provides this too), then run llama.cpp's
`convert_hf_to_gguf.py` and `llama-quantize` yourself to get a `.gguf` file at whatever
quantization you want (q4_k_m is a reasonable default, matching typical Ollama model sizes).

Either way, once you have a `.gguf` file, create an Ollama Modelfile:

```
# Modelfile
FROM ./smallbiz-assistant-lora.gguf
```

then:

```
ollama create smallbiz-assistant-lora -f Modelfile
```

## 5. Run the Phase 2 eval harness against it - the actual acceptance test

From the Mac, in the existing `.venv` (same tooling as Phase 2, nothing new to install):

```
caffeinate -i env CHAT_MODEL=smallbiz-assistant-lora python evaluate.py
python compare_runs.py data/eval/runs/20260923-121731_llama3.1-8b data/eval/runs/<new run folder>
```

This runs the untouched 216-question `eval_set.jsonl` against the fine-tuned model exactly
the way the 94% baseline was measured, then diffs the two runs question-by-question -
regressions and improvements both show up explicitly, same as every prompt-tweak comparison
done in Phase 2.

**What "success" looks like**: overall pass rate at or above 94% (203/215), AND no new
regressions on categories the baseline already handled well - a same-or-better score that
trades away correctness somewhere else isn't actually a win. Specifically worth checking:
whether the fine-tune moved the needle on the known over-hedging weak spot (F021, F060, N011,
U015) without breaking anything else, and whether the followup category (stuck at 73% through
Phase 2) improved.

If the result looks good: this becomes the new default `CHAT_MODEL` for the app. If not: the
LoRA adapter and both jsonl files are small and cheap to keep around, so this can be re-run
with different hyperparameters (more epochs, different rank, a filtered subset of the training
data) without regenerating anything from Phase 3.
